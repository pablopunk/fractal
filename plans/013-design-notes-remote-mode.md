# Plan 013: Design notes — Remote mode

Goal: run Fractal's backend on one machine (the **host**, e.g. laptop at home) and use it from another device (the **remote**: phone or second laptop), across networks. An instance is either host or remote, never mixed.

Decisions already made:

- **Tunneling: Tailscale.** Fractal does no NAT traversal itself; both devices join the same tailnet and the host is reachable at its MagicDNS name (e.g. `laptop.tail1234.ts.net`).
- **Clients: both.** The existing web UI becomes installable as a PWA (phone), and the Electron app gains a remote mode (second laptop). Same SPA code either way — the only difference is which base URL it talks to.

## Q1: What is the client↔backend protocol?

**Recommendation: the protocol already exists — HTTP REST + WebSocket. The work is consolidating it behind one origin, not inventing a new protocol.**

Current state is unusually clean: the React SPA talks to the Astro Node server exclusively through `/api/*` REST endpoints; no component imports server code; Electron IPC carries only `openExternal`, `getPathForFile`, and `terminalPort`. A browser pointed at the server already works for everything except the terminal.

The one violation of "one base URL" is the terminal: `main.cjs` spawns `terminal-server.cjs` on a random localhost port (`main.cjs:219`) and passes it to the renderer via preload args; `TerminalPane.tsx:458` then dials `ws://127.0.0.1:${port}/terminal`. That design is unreachable remotely by construction.

**Change:** mount the terminal WS on the main server's origin at a fixed path (`/api/terminal/ws`), either by having the Astro Node server own the WS upgrade or by proxying upgrades on that path to the internal terminal server. After this, the entire protocol is "one origin, HTTP + WS", and switching backends is literally switching a base URL.

The preload `terminalPort` plumbing and the `ws://127.0.0.1` literal go away; the client derives the WS URL from `window.location` (or the configured remote base URL): `wss?://<base>/api/terminal/ws`.

## Q2: Host mode vs remote mode

**Recommendation: a single `mode` in settings — `host` (default, current behavior) or `remote` (no local backend, just a base URL + token).**

- **Host mode (Electron):** exactly today, plus optionally "remote access enabled". When enabled, the server binds the Tailscale interface instead of `127.0.0.1` and requires the access token (Q3). Binding the tailnet IP specifically (from `tailscale status --json`) is preferable to `0.0.0.0` — LAN strangers never get a TCP connection at all.
- **Remote mode (Electron):** skip starting the Astro server, terminal server, and SQLite entirely; `loadURL(remoteBaseUrl)` and let the host serve the SPA. The second laptop is then just a chrome around the host's UI — zero risk of state divergence, no sync problem.
- **Remote mode (phone):** the browser *is* remote mode. Visit the host URL, install as PWA.

Serving the SPA from the host (rather than bundling client code in the remote Electron app) means remote clients never version-skew against the API: the host always serves matching client + server. This kills the need for API versioning for now.

## Q3: Auth

**Recommendation: a single long-lived bearer token generated by the host, required whenever the server is not bound to localhost.**

Tailscale already gives encryption + device-level identity, so this is defense in depth (a stolen device on the tailnet, a misconfigured shared tailnet node), not the primary wall. Keep it simple:

- Host generates a random token on first "enable remote access", stores it in settings, shows it in the UI (and in the QR, Q4).
- Middleware on the Node server: requests from non-localhost must carry `Authorization: Bearer <token>` (or `?token=` for the WS upgrade, since browser WS can't set headers). Localhost requests stay unauthenticated — the local Electron host UI keeps working untouched.
- Client stores the token (localStorage / Electron settings) after pairing.

Passkeys/OAuth are overbuilt for a personal single-user tool riding on a private tailnet. If Fractal ever exposes itself on a public tunnel (Cloudflare), revisit.

### HTTPS

PWA installation and clipboard/notification APIs want a secure context. `tailscale serve` solves this for free: it terminates TLS with a real `*.ts.net` cert and proxies to the local port. The recommended setup is therefore: Fractal binds localhost as today, `tailscale serve --bg https / http://127.0.0.1:7666` exposes it tailnet-wide over HTTPS. Fractal can shell out to set this up automatically when remote access is enabled (and detect "Tailscale not installed/running" → guide the user). This also removes the need to bind non-localhost at all — `tailscale serve` is the only doorway, which is the safest shape.

## Q4: Pairing UX (auto-discover / QR)

**Recommendation: QR code for phones, MagicDNS auto-detect for laptops; both encode the same connect URL.**

When the user enables remote access on the host, Fractal:

1. Runs `tailscale status --json` (or the LocalAPI socket) to get the host's MagicDNS name and tailnet IP. No mDNS/Bonjour needed — Tailscale *is* the discovery mechanism, and it works across networks where mDNS can't.
2. Sets up `tailscale serve` (Q3) so the URL is `https://laptop.tail1234.ts.net`.
3. Shows a **QR code** encoding `https://laptop.tail1234.ts.net/connect#token=<token>`. Phone (already on the tailnet via the Tailscale app) scans it, lands on a `/connect` page served by the host, which stashes the token from the fragment into localStorage and prompts "Install as app". Token in the URL *fragment* never hits server logs.
4. The same panel shows the URL + token as copyable text for the second-laptop flow: Electron remote mode asks for a URL, and can also offer a picker by running `tailscale status --json` locally and probing peers for a Fractal health endpoint (`GET /api/health`, unauthenticated, returns app name + version) — that's the "auto-discover" experience on devices that have the CLI.

QR generation is a tiny dependency (`qrcode` npm package) rendered in a settings modal.

## Q5: What breaks remotely, and what we explicitly punt on

Known work items beyond the above:

- `TerminalPane.tsx` WS URL derivation (Q1) and any other absolute `127.0.0.1` references in client code (`url-preview.ts` is server-side, fine).
- Electron-only niceties degrade gracefully in the browser: `openExternal` falls back to `window.open`, `getPathForFile` (drag-drop of local files) is host-machine-only and should hide in remote mode.
- Mobile layout: the UI is desktop-shaped; a usable phone experience (sidebar → drawer, terminal touch handling) is its own follow-up plan, not part of the protocol work.

Explicit non-goals for v1: multi-user/concurrent-write semantics (single SQLite, single owner is fine — last write wins between your own devices), public-internet exposure, native mobile app, offline support in the PWA.

## Q6: Host availability (sleep)

**Recommendation: a "Keep Mac awake" toggle in settings; while enabled and the app is running, the host spawns `caffeinate -i` as a child process.**

`-i` prevents idle sleep but still allows display sleep, so the laptop isn't burning its screen all night. Kill the child on app quit and on toggle-off (and it dies with the process anyway, so no orphan risk). Lid-close on AC power respects `caffeinate -i` on modern macOS via `caffeinate -s` semantics — use `-s` (prevent system sleep, AC-only) alongside `-i` so the common "lid closed, plugged in at home" case keeps the server alive; on battery, macOS will sleep regardless, which is the right default.

The toggle lives next to "Enable remote access" but is independent of it (useful for long local agent runs too). Linux equivalent (`systemd-inhibit`) can come later.

Client side, the remote SPA needs a graceful "host unreachable" state regardless: exponential-backoff reconnect for the terminal WS and a thin banner ("reconnecting to laptop…") instead of a broken UI, since even a caffeinated host reboots or drops off the tailnet occasionally.

## Phasing

1. **Terminal behind the main origin** — removes the preload port plumbing; pure refactor, fully testable locally.
2. **Token middleware + `/api/health` + `/connect` page** — server-side remote plumbing.
3. **Enable-remote-access settings panel** — tailscale detection, `tailscale serve` setup, QR/URL display.
4. **PWA manifest + browser fallbacks** for Electron-only APIs, plus the reconnect banner.
5. **Electron remote mode** — mode picker on launch, `loadURL(remote)`.
6. **Keep-awake toggle** — `caffeinate -is` child process (Q6).
7. **Mobile layout pass** (separate plan).

Phases 1–2 are useful even if remote mode never ships (cleaner architecture, health endpoint); each phase is independently shippable.
